# LeagueAkari 功能复刻与现有界面融合方案

调研日期：2026-10-21。状态：研究与建议，尚未作为实现范围确认；未修改生产代码。

参考对象：[LeagueAkari](https://github.com/LeagueAkari/LeagueAkari)，本地只读副本位于 `.cache/league-akari-reference`（不进入版本控制）。核对基线为 `dev` 分支提交 `56cdfde00e56148f4641d1a8cf86acb66e903124`；发布页当前标记稳定版 v1.5.1，开发包版本为 1.5.2-beta，二者不混同。

## 1. 结论与范围假设

目标是把当前国服皮肤助手扩展成综合客户端助手，让玩家在一个窗口完成选皮肤、看本局、查战绩和配置自动操作。沿用已选择的 A「沉浸衣橱」方向：深墨蓝、金色重点、窄图标导航、衣橱原画舞台。

用户尚未指定第一期功能顺序；本方案暂按“分阶段覆盖主要能力、Windows 国服优先、继续现有设计”评估。功能对标与复制实现需要区分：上游 Electron/Vue/MobX 与当前 Tauri/Rust/TypeScript 的运行环境不同，其窗口、通信、原生输入、后台调度层不能直接搬入。

关键事实：上游当前 README 和官网明确声明不支持腾讯运营区服。源码仍存在 TENCENT 分支和国服测试夹具，它们只能作为研究线索，不能证明当前国服兼容。跨区查询、战绩时间线、选人身份、各模式写接口必须独立验证。

## 2. 已核对功能与差距

| 功能组 | 上游已发现的能力 | 当前项目情况 | 建议落点与阶段 |
| --- | --- | --- | --- |
| 玩家与战绩 | 玩家搜索、多玩家标签、模式/英雄/位置/时间筛选、详情、装备、时间线 | 已有本人资料、段位及近期记录摘要 | 扩展个人信息为玩家页；第一期 |
| 本局分析 | 选人/游戏中玩家信息、战绩、KDA、常用英雄、队伍统计、玩家标记、推断组队 | 现有快照侧重本人英雄和皮肤，没有完整队伍模型 | 游戏辅助增加“本局分析”；第一期先读可见成员 |
| 游戏流程自动化 | 自动接受、匹配/重排、重连、再来一局、荣誉、邀请处理 | 自动接受及 0–5 秒延迟已实现，其他待做 | 自动化子页；第二期逐项补齐 |
| 自动选禁 | 模式和位置配置、英雄优先级、预选/亮出/锁定策略、延迟、备战席和交换 | 未实现 | 自动化子页；第二期先排位基础选禁，再扩模式 |
| 英雄配置 | 按英雄/模式/位置保存并应用符文、召唤师技能；OP.GG 推荐/装备相关能力 | 已有国服官方榜单和海克斯攻略，尚无配置写入 | 沿用现有攻略数据，补手动应用，再补自动预设 |
| 工具集 | 客户端、房间、好友、奖励领取、资料背景、聊天、游戏中发送等 | 已有重连、托盘、开机启动和缓存清理 | 新增工具入口；第三期按国服可用性选择 |
| 游戏中辅助 | 对局独立窗、计时窗、快捷键、复活相关信息 | 无独立对局窗和全局快捷键体系 | 第三期独立评估，只在可用数据支持下实现 |
| 高级分析 | Akari 评分、打野路线、历史关系与组队推断 | 当前是基础统计 | 在摘要、详情、时间线可靠后追加，不阻塞基础体验 |

注意：上游工具集的 `loot-tools` 被 `import.meta.env.DEV` 限定为开发环境入口，不应把它列为稳定版默认能力。上游支持的模式也不等于我们已验证的模式。

## 3. 实现方式和架构取舍

### 3.1 保留当前应用基础

```text
玩家
  |
  v
Tauri 桌面助手 ---- 本机 LCU ---- 国服英雄联盟客户端
  |                   |
  |                   +---- 已验证的接口能力
  +---- 国服官方攻略来源
  +---- 本地配置、玩家标记、限量缓存
```

```text
TypeScript 界面：玩家 / 衣橱 / 本局 / 自动化 / 攻略 / 工具
                    |
            明确的业务 IPC 与事件
                    |
Rust：连接会话 + 状态中心 + 请求调度 + 自动操作执行器
        |             |                 |
        v             v                 v
     LCU 适配      玩家/战绩服务     自动接受/选禁/配置
        |
     本地客户端
```

继续本地模块化单体。先拆分 `ui/src/main.ts` 中的页面职责，再增加新页面；当前 `profile.rs` 面向本人摘要，应扩展独立的玩家查询和对局详情服务，避免让原快照同时承担皮肤目录和全体战绩。

### 3.2 借鉴上游的业务边界

| 上游路径（相对其仓库） | 可借鉴内容 | 当前落地方式 |
| --- | --- | --- |
| `src/main/shards/league-client` | HTTP、事件、状态同步与重连 | 扩展当前 Rust LCU 适配与会话状态 |
| `src/shared/data-adapter` | 多来源数据归一化、统计和评分 | 先定义本项目 DTO，再提取适用纯计算函数与测试；剥离别名和上游类型依赖 |
| `src/main/shards/ongoing-game` | 分离摘要/详情加载、请求取消、队伍分析 | 新增本局服务及独立事件，按成员渐进更新 |
| `src/main/shards/auto-select` | 候选资格、位置优先级、阶段时间校准 | 用 Rust 实现计划与执行；保留国服模式适配 |
| `src/main/shards/auto-gameflow` | 按游戏阶段安排并取消任务 | 扩展当前自动接受后台，统一任务取消和日志格式 |
| `src/main/shards/auto-champ-config` | 按英雄/模式/位置选择符文与技能预设 | 建立预设服务，先手动应用并核对，再做自动应用 |
| `src/main/shards/saved-player`、`storage` | 玩家标记、遇到记录、持久化与迁移 | 简单开关继续 JSON；需要关系查询和积累数据时加入 SQLite |
| `src/main/shards/window-manager` | 独立窗生命周期、位置保存 | 用 Tauri 窗口 API 重新实现 |

采用此方式的代价：需要改写 Electron 专用部分；收益是可以继续使用现有已验证的国服连接、皮肤链路和设计。前端框架迁移不作为复刻前置条件，先按页面拆分 TypeScript 模块。

### 3.3 先做国服能力验证

先验证只读链路：可见成员身份 → 玩家资料/段位 → 历史列表 → 单场详情 → 时间线。上游的 LCU 战绩封装包括：

- `/lol-match-history/v1/products/lol/{puuid}/matches`
- `/lol-match-history/v1/games/{gameId}`
- `/lol-match-history/v1/game-timelines/{gameId}`

这些是上游调用路径，并非本轮已在真实国服验证的承诺。玩家搜索、跨区和更多历史数据还可能依赖 SGP 服务地址、令牌和区服配置，不以“有 PUUID”推断一定可查。

为每种能力记录支持、不可用、暂时失败和未知。选人阶段接口没有返回的身份保留为未知；晚到的响应不能覆盖新账号、新对局或新查询的状态。基础评分和打野路线依赖的字段不完整时，不填充虚构数值。组队推断显示样本与推断性质。

### 3.4 状态和请求调度

当前 Rust 实际使用轮询（选人/确认阶段 180ms、其他阶段 650ms，加请求耗时）。功能增多后，采用一个 LCU WebSocket 会话接收状态变化，再保留低频完整读取校准；初始快照、订阅期间事件、重连代次需要统一处理。

上游实际订阅通用 `OnJsonApiEvent`，源码说明细分 champ-select 事件订阅存在时机问题。实现时可参考此现象，不能假定每个细分订阅都可靠；同样不能在本轮未实测情况下保证通用事件适用于所有国服版本。

读取与写入分开排队。自动接受和选禁检查具有高优先级，背景战绩/图片请求不能阻塞时间敏感操作。建议先展示成员与摘要，再按需加载详情；以 10 人各 20 场估算，有约 200 条摘要，若逐场立即请求详情则可能再产生大量请求，需要合并相同 gameId、限并发、取消旧会话请求和缓存。此为工作量估算，不是实测请求数或性能承诺。

### 3.5 自动操作闭环

```text
阶段/配置变化 → 计算候选与截止时间 → 展示待执行任务
  → 到时重读当前动作/资格 → 发送一次 → 核对结果 → 更新日志
```

选禁操作需要同时检查账号/连接代次、选人会话、本人 cellId、actionId、动作类型、是否轮到本人、候选是否仍可选/可禁和阶段剩余时间。被禁、被抢、队友预选或手动更改应使原计划失效并按明确策略处理。关闭开关和退出阶段会取消待执行任务。

借鉴上游“实际延迟受阶段剩余时间限制”的做法，预留请求时间；超过有效窗口则停做。写请求结果未知时先核对，不做通用自动重试。符文、技能、皮肤作为不同动作分别汇报结果，不把多步配置假装成原子事务。

## 4. 与已选设计融合

### 4.1 导航结构建议

```text
玩家（现有个人信息）
  我的概览 / 玩家查询 / 战绩与详情 / 标记
对局（现有游戏辅助）
  皮肤衣橱 / 本局分析 / 自动化
攻略（现有游戏资讯）
  峡谷 / 海克斯 / 极地 / 经典
工具（新增）
  客户端 / 房间与好友 / 资料 / 奖励
设置
  外观 / 通用行为 / 数据 / 快捷键
```

以上是信息结构建议，名称与入口数量尚待确认。主要侧栏控制为五项，功能变多通过页内标签组织。自动化详细配置统一放在自动化页，衣橱底部只放高频快捷状态；设置页可提供跳转，避免多个编辑器重复维护不同状态。

### 4.2 各页的视觉职责

- 衣橱继续突出原画、预览、横向皮肤带和确认操作。
- 本局分析采用短标题区、阵营/成员列表、玩家摘要、按需展开的详情。原画作为小面积英雄封面，不在数据表后面铺高对比背景。
- 玩家页沿用当前头像和段位区，下方加入战绩列表；点一场再展开双方详情、装备和图表。
- 自动化页采用任务列表和配置面板，显示是否启用、适用模式、下一动作、执行状态和暂停本局；高级选项折叠。
- 攻略页保留当前国服数据来源，增加“应用符文/保存预设”等上下文动作；仅当数据完整且写接口已验证时开放。
- 工具以少量分组列表呈现，任务完成后统一进入操作日志；批量删除、消耗资产等不可逆行为必须先提供明确预览及必要确认。

沿用蓝金色、字体层级、细边框和间距。金色用于当前焦点和主要动作，胜负/错误使用语义色；玩家首屏保留段位、近期胜率、KDA、常用英雄等少数核心指标，其余展开。评分标注算法来源，不能让用户误认为官方评分或胜负预测。

### 4.3 适配现有窗口

980×700 默认使用紧凑玩家行或两列卡片，选择一名玩家再展开；760×560 使用单列与阵营切换。五人横排适合作为足够宽窗口下的可选布局，不能要求十张完整卡片在默认窗口同时展示全部统计。

本局分析与衣橱共享游戏上下文，但分别保存滚动与选中状态。进入选人时仍能直接看到衣橱；阶段变化通过状态提示或用户配置的自动切换处理，避免打断玩家手动浏览。当前离开选人会隐藏窗口的策略，也需扩展为“衣橱模式”和“本局模式”各自的可见性规则。

## 5. 分期与验收

| 阶段 | 输出 | 验收重点 |
| --- | --- | --- |
| 0：验证与拆分 | 国服能力矩阵、统一成员/战绩模型、页面拆分、会话取消机制 | 缺字段/断线明确降级；现有换肤和自动接受通过回归 |
| 1：玩家与本局 | 玩家查询、战绩列表/详情、可见成员分析、基础标记 | 每项数据来源和样本可查；换账号/换对局不会串数据；小窗口可用 |
| 2：自动化与配置 | 模式/位置英雄优先级、自动选禁、手动符文/技能应用及自动预设 | 只作用于本人的有效动作；手动操作优先；退出阶段取消；未知结果核对 |
| 3：工具和进阶 | 按可用性逐项增加流程自动化、工具、独立窗、关系/时间线分析 | 每项独立开关/失败处理；批量操作预览；不会拖慢接受和选禁 |

本轮不承诺全量一比一兼容，也不按上游截图推断当前国服一定有对应数据。主要风险按先后为：数据不可得、自动操作会话失效、批量查询拖慢关键操作、界面信息过载、长期接口维护成本。
